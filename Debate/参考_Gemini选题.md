这份方案**在立项论证与答辩叙事层面的可行性极高（接近满分），在单卡 8GB 的工程代码落地层面也完全跑得通**，但存在 **4 个隐藏的“代码级暗雷”和 1 处文档细节穿帮**。只要在动手写代码和最终提交文档前把这几个点微调好，这就是一份非常扎实、抗问询能力极强的方案。

### 一、 为什么说这个方案在“立项与叙事”上非常稳？

1.  **“痛点咬合链”逻辑极其严密**： 评审最怕看到把 5 篇论文生硬拼凑成流水线（A+B+C+D+E）。而你设计的“跨文献痛点闭环互补网络”直接拿前一篇论文 `Limitations` 原文的痛点作为后一篇论文的切入点——特别是用 **Entropy-Based Decoding 的多上下文熵权集成** 去消解 **DUR 对检索集内部排列顺序敏感（Lost in the Middle）** 的问题，以及用 **DUR 的长尾不确定度感知** 去弥补 **TeRDy 无法泛化至未见实体（Transductive 局限）** 的短板，在逻辑上非常自洽。   
2.  **全链路 Training-Free 契合 8GB 硬件人设**： 所选的 5 篇核心方法（TimeR^4 重写、TeRDy 离散频域变换、DUR 不确定度打分、Null-Shot 提示注入、Entropy 对比解码）在推理侧均可设计为**免微调（Training-Free）白盒公式计算**，避开了在 8GB 显存上做 LoRA 或训练额外 Router 网络的显存黑洞。   
3.  **预判防御做得好**： 文档末尾主动列出的 4 个缺陷预案（Lomb-Scargle 非均匀频谱分析、置信度门控早停、拒答阈值 $\tau_{\text{abstain}}$、4-bit 量化锚点）基本提前堵死了评委 80% 的刁钻提问角度。   

### 二、 必须在落地前排掉的 4 个“代码级暗雷”与修改建议

如果你接下来要真正写代码跑实验，或者面对懂底层推理框架的硬核评委，以下 4 个地方按文档字面写代码会踩坑，建议直接按下面的方案做工程平滑：

#### 1. 暗雷一（最致命）：阶段三的 $\Delta \mathbf{A}^{(l)}$ 矩阵差分与 FlashAttention-2 存在底层冲突

-   **问题所在**： 你在显存账本里声明使用了 **FlashAttention-2 与 PagedAttention** 来把 4096 窗口的 KV Cache 压到 `0.85 GB`；但在阶段三的公式里，写的是显式提取第 $l$ 层注意力矩阵做减法：$\Delta \mathbf{A}^{(l)} = \text{Softmax}(\dots) - \text{Softmax}(\dots)$。 在 PyTorch / HuggingFace 中，FlashAttention 的核心原理是算子融合（在 SRAM 中直接完成 $QK^\top$ 与 $V$ 的相乘），**绝不在显存中实例化完整的 $N \times N$ 注意力权重矩阵**。一旦你在代码里开启 `output_attentions=True` 去拦截并修改 $\mathbf{A}^{(l)}$，框架会自动退回 Eager Attention，4096 长度下的注意力矩阵会瞬间撑爆 8GB 显存。   
-   **化解方案**： 回到 `Null-Shot Prompting (2024.emnlp-main.740)` 的原文机制——它本质上是通过在 Prompt 中注入置空语义前缀（Null-Shot Phrase），**隐式诱导**内部注意力重分布，并不需要手动拦截修改中间层张量。   
    -   **文档与代码对策**：将公式 $\Delta \mathbf{A}^{(l)}$ 定义为“机理可解释性探针（仅在短文本离线分析可视化时开启）”；而在实机推理流水线中，保持纯正的 Prompt 前缀注入，或者将置空基准的差分直接下移到 **Logits 层**（与阶段四的无文档先验 $p_\theta(y_t \mid x, y_{<t})$ 合并为一次前向传播）。这样既保留了漂亮公式，又完全兼容 FlashAttention-2。   

#### 2. 暗雷二：阶段一 TeRDy 频域分解从“图补全训练”到“免训练 RAG”的模态断层

-   **问题所在**： `TeRDy (2025.acl-long.473)` 原文是一个**有监督时序知识图谱补全（TKGC）模型**，它的公式 $\phi_{\text{TeRDy}}(e_s, r, e_o, t)$ 依赖于在连续时间步上联合训练出来的关系嵌入 $\mathbf{r}(t)$ 和参数矩阵 $\mathbf{W}_r$。而在你的 A 股财报 RAG 场景中，如果从头训练一个 TKGC 模型，不仅构建全量四元组工程量极大，而且每季新财报发布都要重训。   

-   **化解方案**：

    在实现时采用“轻量级时序语义/数值序列频域解耦”：

    1.  针对检索到的同一财务指标跨期序列（例如某公司过去 8 个季度的“扣非净利润”四元组或文本块），按时间轴排列其稠密编码向量序列 $[\mathbf{e}(t_1), \mathbf{e}(t_2), \dots, \mathbf{e}(t_N)]$（以及对应的财务数值序列）。
    2.  在 CPU 上沿着**时间维度 $N$**（而不是向量维度 $d$）做一维快速傅里叶变换（1D-FFT），分离出低频均值趋势向量 $\mathbf{e}_{\text{low}}$ 与高频残差突变向量 $\mathbf{e}_{\text{high}}$。   
    3.  将原公式中的可学习矩阵 $\mathbf{W}_r$ 替换为**免训练的双线性余弦匹配**，直接作为 `TimeR^4` 第二阶段 TKS 召回的频域重排打分项。这样完全不需要训练图嵌入，100% 契合你写的“CPU 离散变换 + Zero GPU Overhead”。   

#### 3. 暗雷三：阶段二（DUR）与阶段四（Entropy 解码）叠加带来的推理延迟与批次显存

-   **问题所在**：
    -   **显存账本细节**：阶段四需要对 $K=4$ 个候选文档分别计算条件概率 $p_\theta(y_t \mid d_j, x, y_{<t})$，同时还要计算 1 个无文档先验 $p_\theta(y_t \mid x, y_{<t})$。这意味着解码时的实际并发 **Batch Size = $K + 1 = 5$**。此外，如果在 Windows 系统下跑 RTX 3070/4060，桌面窗口管理器（DWM）通常会强占 `0.8 ~ 1.2 GB` 显存，可用显存往往只有 `6.8 ~ 7.0 GB` 左右，`7.70 GB` 的预算在 Windows 下容易触发 OOM 或掉入共享内存导致极度卡顿。   
    -   **计算耗时细节**：阶段二 DUR 公式中含有 $\mathbb{E}_{y \sim p(\cdot \mid x, d)}[-\log p_\theta(y \mid x, d)]$。如果对初筛召回的 20 个候选文档都用 7B 模型自回归采样生成一遍答案 $y$ 来算不确定度，单次问答耗时会高达数十秒。   
-   **化解方案**：
    -   **DUR 加速**：在阶段二计算不确定度时，**不做自回归生成 $y$**，而是只对 `[Query + Document]` 做**单步 Prefill 前向传播**，直接取最后一个 Token 预测分布的香农熵与 Top-$K$ 概率方差来替代生成采样期望。这只需要 1 次 Forward，耗时从几十秒降到毫秒级。
    -   **显存瘦身**：
        1.  将检索器直接放进 CPU（用 ONNX Runtime 跑 `bge-small` 仅需十几毫秒），省下 `0.35 GB` GPU 显存。   
        2.  在文档中补充说明：得益于 **Qwen2.5-7B 的 GQA（分组查询注意力，仅 4 个 KV Heads）** 架构，5 路并发（每路 1024 tokens）在 FP16 下的真实 KV Cache 仅占约 `0.28 GB`（远低于传统 MHA 的 `0.85 GB`），从而把总显存峰值压到 **`6.5 GB` 以内**，即便在 Windows 笔记本的 RTX 4060 上也能稳如泰山。   

#### 4. 暗雷四（文档穿帮点）：中文金融场景配了纯英文向量模型

-   **问题所在**： 文档开头明确核心场景是 **“A股/港股跨期财报时序因果审计”**，但在第三部分“显存预算分配精算表”第 3 条中，写的检索器却是 **`BGE-Small-en-v1.5 / MiniLM-L6-v2`**。这两个都是纯英文模型，用来检索中文 A 股财报会出现严重的语义塌缩，容易被细心的评委一眼抓出破绽。   
-   **化解方案**： 把文档里的模型名称改成 **`BGE-Small-zh-v1.5`**（处理 A 股中文财报，体积同样仅 ~100MB）或 **`BGE-M3 (Int8/FP16)`**（同时完美支持 A 股简中与港股繁中/英文双语财报）。
